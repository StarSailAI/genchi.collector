# Natalie：常驻验证与采集接入

当前状态：Agent、两个来源解析与候选入库链路已部署；Comic / Music 的 `enabled` 均保持 `false`，日调度尚未启用。已有成功样本，但自动验证和批量访问尚不足以稳定运行。

## 执行路径

`genchi.aggregator` 发现列表与详情；Camoufox 遇到可见验证后保留原页面；独立 `verification-agent` 容器领取短期控制权，读取验证面板，再由原浏览器核验并恢复请求。原文仍由 worker 写入 AllFeeds，产品流程调用原有词表与证据校验，生成待审核候选。

Agent 不持有数据库、邮件或 X 登录凭证。它与 browser 共用镜像文件，独立运行 Python HTTP 客户端，不启动第二个浏览器。内存上限 128MB，没有公网端口。仅代理中的 `/verification` 操作可以改变页面。

## 看图与坐标

本次注册的是 Natalie 九宫格图片点选。浏览器从可见 canvas / image 和按钮取得实际位置；视觉模型先逐格辨认物体，再返回匹配格子的编号，不能生成脚本、网址或任意鼠标指令。仅在原始完整图片上调用一次模型；程序换算单个格子的中心，每次点击后重新观察、检查布局及像素变化，证明题目没有更换后才继续同一组选择。开始按钮使用登记的可见按钮位置，不需要模型调用。

每次操作仍有单次 observationId、截图内容、网址与操作区域校验。程序另外比较点击前后的截图，只有刚点击的格子出现变化、其余面板保持一致时，才记住本次选中状态。选中状态完全由程序记录，避免模型把“应选”误当成“已选”；整题刷新、布局变化或未出现选中变化会停止。提交后只检查原页面恢复，不自动再次提交答案。

正常会话 30 分钟到期后可重建；失败会话进入 6 小时冷却，供后续日采集重新检查，当前任务的重试不能继续点选。不要删除账本、重启浏览器或另建 Run 来延续失败轮次。模糊图片、未知布局、模型错误和超时会留下失败原因，来源任务不能将挑战页当作成功。

## 模型与费用边界

服务器沿用已有 DeepSeek API key，仅验证码分类使用 `deepseek-v4-flash-vision-exp`；正文提取继续使用 `LLM_MODEL`。图片以验证面板截图送到配置的 API，不发送 Cookie、浏览器令牌或整篇新闻。

设置都在项目共享 `.env`：

```dotenv
VERIFICATION_AGENT_ENABLED=true
VERIFICATION_LLM_BASE_URL=
VERIFICATION_LLM_API_KEY=
VERIFICATION_LLM_MODEL=deepseek-v4-flash-vision-exp
VERIFICATION_DAILY_MODEL_CALLS=40
```

空的视觉 endpoint/key 由部署工具解析为已有 `LLM_BASE_URL` / `LLM_API_KEY`，不复制密钥到仓库。视觉模型名称必须显式配置；不能用普通文本模型冒充视觉能力。关闭 Agent 时，部署工具也暂停两个 Natalie 来源。

当前九宫格处理每个中断只调用一次模型，底层硬上限仍为 10 次；单次输出最多 450 token、等待最多 18 秒。全服务每天最多 40 次（UTC 日期）；该日上限可配置为 1–100。已有浏览器规则仍限制 120 秒控制权和每个上下文 12 次点击。账本在 `verification-state` 卷中：先持久化预留调用，再请求模型，网络回复丢失也占额度。重启保留当日计数，旧处理中断标为 abandoned，不重做付费调用。

账本记录模型、次数、耗时、供应商报告的输入/输出 token、受限操作与结果，不记录密钥或原始模型回复。失败请求可能没有 token 用量回执，因此次数上限是主要成本约束；不能把未报告 token 算作零费用。最近一次初始题面与最新面板截图留在同一私有卷用于诊断（各覆盖一张，初始图摘要随 Run 记录），不提交 Git。详见 [DeepSeek 图片接口](https://api-docs.deepseek.com/guides/vision/)。

## 运行检查

在服务器 worker 容器中，使用现有 `BROWSER_API_TOKEN` 调用内部 `http://verification-agent:3004/status`；不要把该端口代理到公网。`/health` 只报告启用与忙闲状态。日志中的 `verification_finished` 表示本次自动处理结束，只有 `status=resolved` 才表示原页面核验通过。

普通网站没有验证时不调用视觉模型。人工桥接仍可用，但同一时间只允许一个操作者；手动诊断前应停止 Agent 服务，并沿用原中断，不能和自动 Agent 同时点击。

部署新源码时，先在无在途任务的窗口构建 browser 镜像，再由部署工具准备环境并启动 `browser verification-agent`。操作脚本、面板能力与旧人工验收说明见 [浏览器验证中断](../operations/browser-verification.md)。

## 来源配置与验收

- 入口为 Comic / Music 首页的主栏新闻卡片；不采侧栏排行、评论页或站外详情。
- 正文使用 `.NA_article_body`，保留活动概要与 `external_link` 官方/票务链接，去掉相关推荐、内嵌旧新闻、分享和搜索推广。`.NA_article_date` 单独保存为日本时区的发布时间，不用活动日期代替。
- 稳定 ID 沿用规范化详情 URL 的 SHA-256；原文版本与 checkpoint 沿用 AllFeeds 幂等写入。跨来源和译名不参与这个 ID。
- 每次最多 12 个详情，最多 4 个复查。Natalie 请求至少间隔 30 秒（包括已有不可变任务快照），HTML 成功后不加载样式、图片和广告脚本；验证码页面保留必需资源。
- 普通 401/403 无可见验证时停止该轮详情扫描，未处理页留在 backlog；404/410 与 429 保持独立语义。30 秒间隔是保守配置，尚未证明能消除全部 403。
- 预备日程为日本时间 13:00 / 13:10，当前均关闭。其他八个聚合/运营方来源保持原日程。
