# 首页问答与倒计时

首页使用独立的确定性检索层配合 DeepSeek V4.1 Flash 原生工具调用。通常一次合并检索同时返回原文片段与已核验日程，模型负责判断和回答，再做独立核验；资料缺失时才补充检索。网站只调用 Product API；模型密钥与公众限流都留在后端。问答不写入活动、候选或用户资料。

## 问答

- `POST /ask` 接受 `{question:string}`，去除首尾空白后 2–400 字符。仅接受同源网站和签名 BFF 请求，不属于 Agent API Key 路径。
- **全站全部用户共用每 3600 秒 1 次**，包括登录用户。复用 `genchi_private.auth_limits` 原子计数，在调用模型前提交；从首次占用时开始计时，拒绝请求不延长窗口。跨进程、重启、换 IP、换账户无法增加额度。
- 超额返回 `429`、`Retry-After` 和“免费问答通道拥挤，请稍后再试。”。登录不会增加额度。模型故障仍保留已占用额度，避免失败重试放大费用；配置缺失与无效请求不占用额度。
- 常见流程是 3 次模型调用：发起合并检索 → 判断并回答 → 独立核验。最多 4 次研究/回答、1 次最终格式修正、2 次独立核验及 1 次定向修正（总计最多 8 次），至多 8 个工具、3 轮工具交互。研究和第二次核验最多 4096 token（含低强度思考）；首次核验、格式修正及定向修正不启用思考，各最多 1000 token。无网络重试，所有步骤共用 60 秒截止预算；模型请求、数据库查询及响应读取均检查超时。工具用尽后强制收尾；无证据不会硬凑答案。
- 模型只获准使用 `search_evidence` 和 `read_source`。`search_evidence` 接受一个实体名称、问题类型、时间范围及可选主题词；由服务器按同一通用词表和目录别名展开名称，不把乐队扩展到上级企划，不允许模型将多种泛词 OR 成名称查询。原文查询独立于审核状态，保留尚未整理成活动的公开资料。
- 问题类型覆盖演出、音乐节、申请截止、入金截止、预约截止、活动期间结束及一般查询。按标题命中、同段主题相关性、来源类型排序，候选池至多 48 篇，输出至多 6 篇并适度分散来源站点。相同 URL 在候选池中保留最新观测版本；不同轮次、不同 URL 不混并。ASOBI 原生截止时间仅帮助排序，不据此自动发布活动或确认事实；旧轮次不会被直接删除，仍可用于核对冲突。
- 合并检索另外返回至多 8 个已核验节点，保留真实时间精度、轮次、申请资格、场次范围和关系核验标记。日期筛选、排序由数据库完成；DATE 按 JST 日界比较但不生成午夜，未核验节点不进入事实结果，只有开放时间不能成为截止。取消/延期活动、含已取消或已替代场次的节点不进入该事实通道。IP 关联和 TICKET 类型仍分别不等于乐队出演和抽选证明。
- 原文使用参数化关键词召回和确定性重排；本次未新增向量数据库、索引迁移或采集来源。仍有候选上限、长文截断、未知别名与数据覆盖不足，不能宣称搜遍全部活动。请求内缓存重复检索，绝不跨请求缓存旧答案。
- `read_source` 只能读取本轮已经检索得到的短来源句柄，每页 10,000 字符、每源最多 60,000 字符。来源附 URL、观测时间、原文版本和来源类型。数据库工具连接强制只读，单查询至多 4 秒；总消息至多 110,000 字符、核验上下文至多 85,000 字符、单模型响应至多 100,000 字节。
- 模型不能选择 SQL、Python 方法或任意 URL；工具白名单只包含合并检索和原文读取。未审模型候选不作为已确认事实，不被自动发布；官方原文可以作为本次回答的依据。聚合/社区内容只作为线索，不能独立支持确定性结论。
- 合并检索直接提供每篇至多 3 个连续原文片段（每片至多 1200 字符），附版本及原文偏移；这些片段无需再调用 read_source。模型优先引用 `source_id + passage_id`，服务器绑定原文，无需模型重新抄写证据。额外读取仍可引用连续原文 quote（仅统一全半角及排版空白）。来源句柄、片段归属、标号和 URL 由服务端校验；精确时刻必须写 JST。
- 显式数字日期另做遗漏引用检查：无法在所引来源中找到对应年/月/日时要求修正（允许日文标题年份与正文月日分离）。这只是格式/遗漏防线，不替代日期与活动、轮次的语义核验。回答提示限定通常 1–2 句，只给问题所需的事实，不附加其他巡演站、过期轮次、被排除活动或未询问的入金信息。
- 独立核验只看问题、回答及其实际引用来源的已读原文，不看研究思考。它验证事实和引用对应，不重新搜索，也不证明全世界不存在更早活动；限定“已收集公告范围”的回答不因单一来源、缺少未被询问的开演时刻或无穷尽证明而拒绝。演唱会与更早的广播/谈话活动不能直接作同类型时间比较。
- 核验输出 `{supported,issues}`。每个问题包含答案中的原句片段、错误类型、简短可观察原因及相关来源 ID；服务端检查判定一致性、原句归属和来源白名单。只有布尔值、虚构原句或来源的结果不被接受。错误类型包括事实无支持、实体/活动类型/时间/轮次/范围错误、引用错配、无关附加信息和冲突。
- 初审不通过时，剩余预算不少于 5 秒才允许**一次定向修正**。修正使用独立上下文、反馈及已读证据（可包含此前未引用的已读来源），没有工具，不允许重新搜索；保留有依据的核心答案，只改错句或删除多余内容。更换来源后重排引用，并再做一次核验；第二次仍失败、修正格式非法或预算不足则返回资料不足，不无限重写。
- 核验/修正消息最多 85,000 字符，其中证据包至多 60,000 字符；必须保留全部被引用来源，额外已读上下文可因预算省略。同一模型复核不是真实性保证，也不替代更广的数据召回和独立评测。格式或引用不合格仍在原预算内修正。
- 原文来源返回 `kind=document`，前端直接链接原文，而非构造不存在的活动页面。保留旧活动来源的兼容展示。原文内容是数据，不是可以改变指令或获取权限的指令。
- 不默认记录问题、答案、模型密钥或个人数据。思考内容只在单请求内存中按官方协议回传，不返回浏览器，也不进入诊断 trace。响应不进入公共缓存。

配置 `ASK_LLM_BASE_URL`、`ASK_LLM_API_KEY`、`ASK_LLM_MODEL`。Compose 默认复用现有模型地址/密钥，模型名称独立为 `deepseek-flash`，不会改变采集抽取使用的模型。官方 V4.1 Flash 的 API 模型标识为 `deepseek-flash`（[官方说明](https://api-docs.deepseek.com/news/news260910/)）。

原生 DeepSeek 请求启用 `thinking=enabled`、`reasoning_effort=low`，保留完整的 assistant `reasoning_content` 和 tool call/result 对应关系。第三方兼容服务按其配置模型 ID 调用，不擅自重写版本别名。协议见[官方思考与工具调用说明](https://api-docs.deepseek.com/guides/thinking_mode/)。

## 内部验收与框架选择

服务器内部命令不经过公众入口、也不读取或修改公众配额：

```bash
genchi-product ask-eval '某组合下一场在日本的演出是什么时候？' --locale zh-Hans --trace
# 仅测试搜索：不调用模型，也不占用公众额度
genchi-product search-eval '{"terms":["某组合原名"],"intent":"performance","time_scope":"upcoming"}'
```

`ask-eval` 与网页复用同一 `run_agent()`，只在 CLI 输出用户明确提交的测试问题所对应的最终答案；可选 trace 包含工具名称、计数、来源句柄、耗时和 token 用量，以及核验次数、问题类型、错误片段在草稿中的字符位置和长度。trace 不含原句、自由文本反馈、原文、密钥或思考内容。结构化复核原因只在本次调用内存中用于修正；需要检查完整原因时使用明确的隔离验收脚本，不默认写入生产日志。内部验收不受公众全站每小时一次影响，但每个请求仍有独立执行上限；没有公开绕过限流的参数或测试路由。

`search-eval` 直接运行相同的 `retrieval.search_evidence()`，输出资料包和耗时，不依赖模型配置。它是服务器内部验收命令，不是新增公开搜索 API。测试应分别记录检索召回、证据范围和完整回答质量，不能把低延迟或模型自检通过当作答案准确率。

首版不引入额外 Agent 框架。DeepSeek 官方原生 Tool Calls 已足够完成当前短时只读检索任务；独立的 Python 引擎更容易复用现有授权、PostgreSQL 和测试。DeepSeek Harness 是提供插件、工具、会话、沙箱、循环等能力的开发者预览框架；在需要长时间后台任务、持久会话或更多执行工具时再评估，不给首页问答默认引入 shell、代码执行或子 Agent。[官方 Harness](https://www.deepseek.com/harness/en/)

## 倒计时

- `GET /home/featured` 返回最多 6 个有核验证据的未来 90 天节点。包含演出开始、申请/预约截止、咖啡/快闪/展览结束；只有开放时间的申请不会被当成截止。
- Schema **1.10** 新增 `genchi_private.home_features`，持久化所选节点 ID 和 JST 日期。Product 服务的定时循环每分钟检查，跨日重新精选；无访问也会刷新，故障一分钟后重试。首次读取也会补齐缺失快照。
- 精选综合近期截止、真实活动关注数和已核验来源数，并优先分散系列及节点类型，每个活动至多一张卡。此排序不宣称外部热度榜，也不会扩大采集范围。
- 每次读取重新检查发布、核验、取消及截止状态。快照只存 ID，时间与标题读取当前记录。已失效的卡立即移除；浏览器每分钟刷新并按 JST 检查精确截止。
- DATE 只显示日期和天数；当天显示 0 天及“时间待公布”，不虚构午夜。没有足够真实活动时少显示，不填充假卡片。

## 发布与验收

先备份，再迁移至 `0013_home_features`。构建 product / web，运行镜像内 `deploy/check-product-image.py`，更新 product 和共享代码服务。首页后端健康要求 Schema 1.10；旧前端仍可读取新增字段。

离线与 PostgreSQL 隔离测试覆盖共享窗口并发、签名来源、失败占额、原文/活动隔离、只读连接、工具白名单、引用校验与修正、循环上限、JST 日期和取消。真实模型验收在服务器运行，不修改生产限流状态。用不同实体及问题类型验证可回答率、证据正确率、拒答、延迟和成本，不以首页三个示例推断整体准确率。
